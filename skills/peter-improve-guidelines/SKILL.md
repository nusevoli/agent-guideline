# 지침 개선

## 목적과 범위

실제 문제의 원인을 확인하고 필요한 규칙만 개선한다. 규칙 수를 늘리는 것을 성과로 삼지 않는다.
적용 중인 공통·프로젝트 지침을 확인한다. 이 스킬이 상위 지침을 대체하거나 추가 실행 권한을 부여하지 않는다.
스킬 호출만으로 파일 수정·실험·위임·커밋·업로드·설치·병합이 모두 승인됐다고 간주하지 않는다.

## 수행 절차

1. **사례 정리:** 사용자 목적·기대 결과·관찰된 행동·차이를 짧게 정리한다. 대화나 파일의 근거와 추정을 구분한다. 이미 합의한 목적은 다시 묻지 않는다.
2. **원인 판단:** 해당 규칙과 실제 읽기·실행 근거를 확인한다. 규칙 누락, 표현의 모호함, 규칙 충돌, 미로딩, 실행 미준수를 구분한다. 근거가 없으면 원인 미확인으로 표시한다. 실패 한 번만으로 문서 구조나 특정 도구를 원인으로 단정하지 않는다.
3. **최소 변경안:** 기존 규칙으로 해결 가능한지 먼저 판단한다. 규칙이 충분하면 로딩·실행·검증 절차 개선을 검토한다. 수정이 필요하면 공통 원칙, 작업별 상세 지침, 프로젝트 설정 중 적절한 위치를 선택한다. 다른 위치에 중복 규칙을 만들지 않는다.
4. **계획 합의:** 변경 문구와 대상 파일, 목적·범위·방법·영향·완료 기준·검증 방법을 축약해 제시한다. 결과를 대화에 보고하는 것과 파일 저장·커밋·외부 반영을 구분한다. 이미 승인된 계획은 반복 승인 없이 수행하고 실질적 변경은 다시 합의한다. 검토·제안만 요청받았다면 변경안에서 마친다.
5. **수정과 검사:** 승인한 파일만 수정한다. 관련 규칙의 중복·충돌, 참조 경로, 변경 범위를 확인한다. 행동 평가가 승인 범위에 포함됐을 때만 [평가 방법](references/evaluation.md)을 읽고 수행한다.
6. **결과 전달:** 변경 내용, 확인한 근거, 검사 결과, 미검증 범위와 후속 담당·행동·조건을 보고한다. 제안·수정·검증·설치·활성화를 구분한다.

## 판단 기준

- 사례의 고유한 표현이나 개인 선호를 모든 작업에 대한 보편 규칙으로 확대하지 않는다.
- 단순한 문제에 모든 전문 역할이나 평가 절차를 동원하지 않는다.
- 비교나 추천의 실패라면 사용자 판단에 필요한 기준, 기존 해결책 확인 여부, 대안 비교, 근거의 충분성을 점검한다. 후보 개수를 고정하거나 특정 제품을 공통 지침에 넣지 않는다.
- 부모 AI의 범위 준수도 평가한다. 자식 에이전트의 성공을 전체 과정의 성공으로 보고하지 않는다.
- 수정안이 아직 시험되지 않았다면 개선 효과를 확정하지 않는다. 이미 읽은 스킬을 적용한 자기 검토와 독립 행동 시험을 구분한다.
